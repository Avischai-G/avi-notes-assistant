# Silent Failures in Multi-Agent Systems: What Coroner Learned from 39 Dead Runs

When an agent system crashes, you know. You get a stack trace, you page someone, you fix it. The ones that wound you are the ones that do not crash. The board still looks alive. No worker died. No error was recorded. Thirty-six hours later somebody notices that nothing has moved.

The corpus behind this piece is 39 real multi-agent runs from the author's own production orchestrator. Those traces are private; what ships in `data/cases/` is a fictional structural twin of them, and the live service serves that twin. In the published corpus, 36 of 39 runs (92%) failed silently. Not by crashing. By stopping. No failure message was ever generated, yet the run never banked another step. The same 36 of 39 holds on the private source corpus. When status quo looks like progress, nobody notices the run is dead until somebody remembers to check.

Coroner is a post-mortem service for that category of failure. Every fifteen minutes, a Cloud Scheduler job hits a sweep endpoint. Any run that is still in a non-terminal state and has not moved for thirty minutes is presumed dead. Six specialized agents, each wired with Google's Agent Development Kit and instructed to challenge rather than confirm, examine the trace and produce a diagnosis: a cause of death, the killing step, what work was abandoned, what could have prevented it, and a concrete restart plan. The six agents run on one model — `gemini-3.5-flash` — with three of them executing in parallel; the diversity is in the prompts and the pipeline, not in the model count. The finished plan is then POSTed to a configured endpoint for resumption, so no human has to notice or push a button in between.

The most interesting finding is also the most uncomfortable one. In 8 of the 39 published cases (20.5%), the cause of death certified by the autopsy system differed from the one recorded by a deterministic rule. The clearest example is run `02266df1`, "Allotment Watering Roster Setup", which recorded its own stopping reason as "The agent's interactive CLI was stopped" — yielding a prior cause of WORKER_TERMINATED. The agent's CLI did stop. The autopsy system, however, examined the trace more carefully and certified that the actual cause was STALLED_ON_USER: the run had handed over all six planned steps to a human user and was waiting politely for feedback that never arrived. When the user did not respond, the CLI timeout stopped the interactive session. The symptom was a stopped CLI. The cause was an unanswered question.

This disagreement is not proof that the model is right in all eight cases. But it demonstrates something worth taking seriously: a single LLM reading a broken trace tends to agree with the first plausible story. The traces often do not include enough information to contradict an early hypothesis.

Coroner's middle stage is deliberately built to challenge that failure mode. Instead of three identical skeptics who would agree with each other and the model, three specialized investigators approach the same hypotheses with three fundamentally different lenses.

The **sequence investigator** asks: does the order of events actually support this hypothesis? It finds the earliest point where the run diverged from a healthy one. Anything that happened after that divergence is a symptom, not a cause. For run `02266df1`, the question was whether a CLI stop can occur before the run asks for feedback. It cannot. The early divergence was the unanswered question, not the late CLI termination.

The **counterfactual investigator** asks: if this cause were removed and nothing else changed, would the run have finished? If the answer is no—if it would have stalled somewhere else anyway—then the hypothesis is a contributor but not the true cause. For a WORKER_TERMINATED verdict to hold, one would have to believe that removing the CLI termination alone would have let the run continue. But the trace shows the CLI stopped because it timed out waiting. Remove the timeout and the fundamental problem remains: the user never answered. The hypothesis fails this lens.

The **alternative investigator** asks: can you construct a different explanation that fits every observation at least as well? For WORKER_TERMINATED, the alternative is straightforward: the run completed its work and handed it over to a human for approval, which is correct behavior. The human did not respond (also observable from the trace). The interactive session timed out waiting for that response (also observable). The timeout itself is not a bug—it is a safety mechanism to prevent zombie processes. A different cause, STALLED_ON_USER, fits all the same observations and is simpler because it does not require inventing a new failure that contradicts the expected behavior.

On the published corpus of 39 cases, triage proposed 93 hypotheses. A majority of the three lenses killed 53 of them (57%). Only 13 of the 93 hypotheses (14%) had non-unanimous verdicts—cases where the three lenses disagreed with each other. Across all three lens-pairs, only 9.3% of pairwise comparisons produced disagreement. Nine cases (23%) contained at least one non-unanimous hypothesis. The system killed more hypotheses than it passed, and disagreement was rare.

The architecture makes this possible. Coroner separates evidence extraction from judgment. The ingest stage—adapting traces, redacting secrets, extracting deterministic signals—contains no model calls. By the time an agent reads the brief, it knows the exact step that was in flight, how many times it retried, what it was told to do, what it reported back, and what the orchestrator's deterministic rules think happened. The agents do not recompute any of that; they reason over the signals rather than deriving them from raw JSON. That boundary means the agents can challenge the recorded stop reason without second-guessing the basic facts.

That boundary is also where the honesty of the headline number comes from, so it is worth drawing precisely. **Deterministic, computed from the trace before any model call is made:** the 36 silent runs — `silent` is `t.is_silent` in `app/findings.py`, which is true when a run is still in `held` or `running` with zero recorded worker failures — and the whole step ledger of 147 planned, 73 banked, 74 abandoned. That is exactly why the 92% figure is defensible: a reader can recompute it from `data/cases/` without making a single model call. **Model judgment, recorded but not independently verified:** every certified cause, and the 36 runs marked `revivable`. Coroner does not run recovered runs to completion, so "revivable" means the reviver thought so, nothing stronger.

The step ledger supports two different readings, and they must not be confused. Pooled across the whole corpus, 73 of 147 planned steps were banked — **49.7% of all planned work**. Averaged per run, across the 33 runs that did not stop on purpose, each run banked a mean of **19.34% of its own plan**. Those are different measurements over different populations, and the gap is real: the pooled ratio ignores runs that never got a plan at all, while the per-run mean counts each of the seven such runs as 0%. Both come from `python -m app.metrics`; neither is "73 of 147 expressed as a percentage" except the first.

Coroner's own code is open, but the source corpus of real production runs remains private. The repository ships a fictional structural twin—a set of invented runs with the same failure patterns and the same step dependencies as the real ones. The live service shows 39 case files generated from that twin, and every published number in this piece is measured against that public corpus, so a reader can reconcile all of them offline. A second pass over the private source corpus found the deterministic measures identical—39 cases, 36 silent, 147/73/74 steps, 8 certified causes differing from the rule prior—and the lens-disagreement measures roughly half as large: 96 hypotheses proposed, 54 killed by majority (56%), 5 of 39 cases with a non-unanimous hypothesis (versus 9 public), and 16 pairwise disagreements out of 288 (5.6%, versus 9.3% public). Those five private figures are the one set of numbers in this piece a reader cannot check, and they are reported here only to show that the twin is not a flattering rewrite. Why the lenses split more often on the twin than on the real traces is not something these measurements answer.

What should have been done differently? The first repair is the one Coroner demonstrates: have a system that sweeps for dead runs at all. 92% of the corpus generated no failure alert. Silent failure is the case most likely to go unnoticed.

The second repair is within the orchestrator itself. If a run is going to hand control to a human and wait forever, record that intentionally. Do not let the reason be inferred after the fact. Coroner can still diagnose intent-wait states, but the orchestrator should not surprise itself. "The user never answered" should be a recorded run status, not something that has to be excavated from the trace.

The third repair is not about traces at all. Runs that hand work over to humans should have a deadline. Thirty days or thirty seconds, whatever fits your operational model, but a hard deadline past which the system does not wait. Let the human decide what happens at that deadline—escalate, abort, retry, or let it continue—but do not let it wait forever without being told. The run does not think it is waiting forever. It just stops, and the world sees only silence.

Coroner is not a fix for all three. It addresses the first (sweeping for the dead) and helps narrow the second (it can read a trace and name the true cause when the stopping reason is misleading). It cannot fix the third; that is an orchestrator responsibility.

The findings available in the public data are sparse by design. Redaction masks recognized private keys, database URIs, bearer tokens, JWTs, cloud access keys, URLs, email addresses, filesystem paths and IP addresses before any model call. Ordinary prose—personal names, business context, operational facts—is not redacted, so anything with free text must be considered sensitive. The rate limit of five autopsies per caller per hour exists because autopsies cost money on the author's card; judges get a separate key, sent as an `X-Coroner-Judge-Key` header, that bypasses that gate.

The code, the metrics, the tests, and the case files are all public. The only thing held back is the real corpus and the exact production traces. The live service is real, running, and accessible. You can point it at a log from your own orchestrator (within the rate limits) and get back a diagnosis. Most likely, Coroner will not find anything new—you already know your system better than any model reading a trace can know it. But if your multi-agent run ever stops moving for reasons you cannot quite name, it exists for that case.
